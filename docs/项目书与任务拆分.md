# CodeReview Tutor 项目书与任务拆分

**项目名：** CodeReview Tutor（仓库仍为 RepoFix-RL）  
**产品方向：** 面向 LeetCode Hot 100 刷题者的代码错误分析与解题复盘 Agent  
**首版语言：** Python 3（C++ 暂缓）
**周期：** 每天 3–4 小时，目标 1–2 周完成可演示 MVP 与一轮小规模后训练实验  
**训练平台：** HKU CS GPU Farm Phase 2；产品开发先在本地完成

## 1. 项目目标

用户正在刷算法题时，提交题目描述、自己的代码和编程语言。Agent 运行可用样例或测试，帮助用户定位错误、构造失败反例、解释根因，并给出分层提示和复盘总结。默认先教学式诊断，不直接替用户重写整份答案；用户可以请求查看修复建议，然后重新运行验证。

项目的研究问题是：**后训练能否提升 Agent 对算法题错误代码的诊断准确性、反例质量和教学解释质量，同时减少对正确代码的误报？**

产品面向 Hot 100 刷题场景，但公开仓库不收录未经许可的力扣题面、官方解答或隐藏测试。用户可在本地会话粘贴题目内容；内置评测集优先使用原创的 LeetCode 风格题目、错误代码、反例及测试。对外描述为“面向 LeetCode Hot 100 刷题者”，不暗示与 LeetCode 官方合作。

## 2. 用户流程

1. 用户粘贴题目描述、样例（可选）和自己的 Python 代码。
2. Agent 先解释它对题意/代码行为的理解，并判断当前代码是否能复现问题。
3. 后端在隔离执行环境中运行代码；记录编译错误、运行错误、超时或样例结果。
4. Agent 给出结构化诊断：问题位置、触发条件/反例、根因、分层提示和解题复盘。
5. 用户可以展开修复建议或提交修改后的代码再次验证。

## 3. MVP 边界

### 必须完成

- Python 3 ACM 模式代码输入与运行。
- 题目描述和代码输入编辑器。
- 后端执行接口与结构化错误/测试结果。
- Agent 诊断、反例解释和复盘输出。
- 显示运行轨迹、测试状态、诊断内容和可选补丁 diff。
- 原创小型评测集与自动评测脚本；报告训练前后对比。

### 暂不做

- 托管、爬取或镜像完整 Hot 100 题库。
- 自动登录或提交代码到 LeetCode。
- 任意语言、任意 GitHub 项目或生产级在线代码托管。
- 公网多用户服务、账户系统和长期保存用户代码。
- 未隔离执行用户任意代码。当前本地原型不适用于不可信公网输入。

## 4. Python 执行设计

采用统一的 `Submission` 请求模型（problem、language、source_code、sample_inputs），并由语言专属 runner 执行：

- **Python runner：** 临时目录写入源文件，以固定入口和限定参数执行；超时后终止进程。
- 当前仅支持 Python runner：临时目录写入源文件，以隔离模式运行；超时后终止进程，并结构化返回 stdout、stderr、耗时和样例结果。
- C++ 支持暂缓，待 Python 诊断与评测闭环稳定后再决定是否恢复。
- 本地 Windows 与 HKU Linux GPU 节点的执行环境不同；部署目标先定为本地开发和 Linux GPU Farm。
- MVP 至少设置超时、工作目录隔离、固定命令、输入大小限制。真正执行不可信代码前必须补足 OS/container 沙箱、内存/进程限制、网络禁用和文件系统限制；不能把临时目录误称为安全沙箱。

## 5. Agent 输出协议

模型返回 JSON，至少包含：

```json
{
  "verdict": "incorrect | likely_correct | cannot_determine",
  "bug_category": "boundary | state | indexing | complexity | parsing | other | none",
  "location": "函数/行号或代码片段",
  "counterexample": {"input": "...", "expected": "...", "actual": "..."},
  "root_cause": "针对提交代码的解释",
  "hints": ["提示一", "提示二"],
  "solution_review": "算法思路、复杂度及可改进点",
  "suggested_patch": "可选；用户请求时再展示"
}
```

不要求模型暴露私有思维链。轨迹记录可展示简短行动摘要、工具调用和验证结果。

## 6. 评测方案

### 基准样本

先制作约 30 个原创 Python 样本；样本成对包括正确解法和含缺陷解法，按题型/错误模板分层。每条记录题意、代码、隐藏测试、参考输出、已知错误类别、缺陷位置、参考反例、诊断要点和许可证/来源。按问题模板拆分 train/validation/test，近似变体不可跨集合。

### 指标

- Verdict accuracy：判断代码正确/错误是否正确。
- False-positive rate：正确代码被误报的比例。
- Bug localization/category F1：缺陷位置与类别准确度。
- Counterexample validity：给出的反例是否能稳定复现问题。
- Test pass rate：诊断建议或补丁应用后隐藏测试通过率。
- Explanation rubric：根因准确、针对用户代码、清晰易懂、提示层次合适、未提前泄露答案（盲评抽样）。
- 编译成功率、运行/超时率、耗时。

不以“修完后全通过”作为唯一指标，也不把模型自己的解释当作其诊断正确的证据。对正确代码样本必须计算误报。

### 后训练奖励候选

可验证奖励来自 verdict、隐藏测试、反例复现、错误类别和位置匹配；解释质量先由人工 rubric 抽查校准，再考虑使用辅助 judge。先跑未训练基线，再考虑 SFT/GRPO。冻结测试集不得用于训练、提示调参或奖励设计。

## 7. 开发与训练节奏（10 个工作日）

| 日 | 主题 | 当日交付 |
|---|---|---|
| 1 | 产品改向、API 与 schema | 新项目书、Submission/Diagnosis JSON schema、数据许可约定 |
| 2 | 输入界面 | Python 代码编辑器、题面和提交 API |
| 3 | Python 执行 runner | 临时工作区、样例运行、超时与结构化输出 |
| 4 | Python Agent 诊断接口 | Ollama 接入、结构化诊断输出、异常处理 |
| 5 | 诊断评测器 | verdict、定位、反例与测试验证指标 |
| 6 | 评测数据 | 首批原创样本、按模板切分、人工抽查 |
| 7 | 基线 | Qwen2.5-Coder 1.5B 在冻结基准上的指标与失败分析 |
| 8 | Python 诊断迭代 | 修复评测中发现的系统性问题，记录失败案例 |
| 9 | 后训练试验 | 按数据/资源成熟度跑 SFT 或小规模 GRPO；记录资源与结果 |
| 10 | 演示与复现 | UI 完整流程、README、实验报告、简历表述 |

如果执行器或评测数据准备占用过多时间，优先保障 Python 输入体验与诊断评测闭环；后训练可以推迟，不能用未验证的训练数字代替结果。

## 8. Git 与数据约定

- 在 RepoFix-RL 目录内开发并本地提交；用户已决定 GPU 阶段再推送服务器所需更新。
- `.env`、API key、用户提交代码、模型权重、缓存和大数据文件不进 Git。
- 公共仓库只保存原创样本、程序代码、许可证和可复现实验摘要。
- 用户输入默认只在本地运行期间处理，不上传到外部服务；本地 Ollama 为默认模型接入方式。

## 9. 当前状态与下一里程碑

已有 React/FastAPI 界面、Ollama + Qwen2.5-Coder 1.5B Provider，以及三个用于验证修复链路的内置 Python 微任务。这些内容是技术原型，不是新的产品主流程或正式评测集。

下一步聚焦 Python 题目描述、用户代码、样例运行和诊断评测。完成执行与结构化评测闭环后，再开始基线及后训练；C++ 暂缓。每阶段提交 Git；服务器同步按用户指定在 GPU 阶段进行。
