# RepoFix-RL 项目书与任务拆分

**项目名称：** RepoFix-RL：面向小型 Python 仓库的可评测代码修复 Agent  
**计划周期：** 10 个工作日，每天约 3–4 小时（约 30–40 小时）  
**目标平台：** HKU CS GPU Farm Phase 2；本地开发、GPU Farm 训练与评测  
**项目定位：** 求职作品与后训练实践原型，不以复刻通用编程 Agent 为目标

## 1. 项目摘要

RepoFix-RL 是一个带有前端和后端的代码修复 Agent。用户从预置的小型 Python 仓库和 bug 任务中选择任务，Agent 阅读代码、搜索相关位置、提出修改、运行测试并提交补丁。界面展示执行步骤、工具输入输出、测试结果、代码 diff 和任务得分。

项目的核心研究问题是：**在固定的小型 Python 修复任务集上，基于可验证测试奖励的 GRPO 是否能提高代码修复成功率？**

项目既交付可演示的软件，也交付可复现的后训练实验。前端和后端负责产品演示与轨迹记录；训练实验聚焦于一个明确、可程序化评测的代码修复任务，避免把“做出界面”误当成模型能力提升。

## 2. 目标与非目标

### 目标

- 提供一个清楚、可现场演示的 Web 界面。
- 完成端到端任务流：选任务、运行 Agent、调用工具、应用补丁、执行测试、查看结果。
- 记录结构化轨迹，支持问题复盘和后训练数据生成。
- 建立固定训练/验证/测试划分和自动评分器。
- 完成基础模型基线，并争取完成 LoRA/QLoRA GRPO 小规模实验。
- 对比训练前后指标，保存配置、日志、模型适配器和代码版本信息。
- 每个可运行里程碑提交 Git；每个工作日结束推送到远程仓库，便于 GPU Farm 克隆和同步。

### 非目标

- 自动修复任意 GitHub 仓库或生产代码。
- 完整复刻 SWE-agent、OpenHands 等大型工程 Agent。
- 多 Agent 协作、复杂长期记忆、浏览器操作或任意 shell 权限。
- 在两周内证明算法普遍优于其他算法。
- 训练或微调大型基础模型；首版以较小代码模型和参数高效微调为目标。

## 3. 首版用户体验

1. 用户进入任务库，选择一个预置 Python 仓库和 bug 描述。
2. 用户点击运行，后端启动隔离工作目录中的 Agent 任务。
3. Agent 通过有限工具读取文件、搜索文本、查看目录、编辑文件和运行指定测试。
4. 页面按时间线展示 Agent 步骤、工具调用、输出、测试状态和运行进度。
5. 任务结束后显示补丁 diff、通过/失败的测试、总分和轨迹下载入口。
6. 用户可查看基线与训练后模型在相同任务集上的对比结果。

## 4. 技术方案（初始建议）

| 层 | 初始方案 | 说明 |
|---|---|---|
| 前端 | React + TypeScript + Vite | 快速构建任务选择、运行状态、轨迹和 diff 展示 |
| 后端 | Python + FastAPI | Agent 调度、工具接口、任务状态、日志与评测 API |
| 任务执行 | 每个任务独立临时工作目录；白名单命令 | 只运行预置项目及指定测试，设置超时和资源上限 |
| 模型调用 | 可切换兼容 OpenAI API 的模型服务/本地推理服务 | Agent 与训练框架解耦；模型服务部署细节待 GPU 环境确认 |
| 训练 | 优先评估 TRL GRPO + PEFT LoRA/QLoRA | 先做最小 smoke run，再扩大 rollout；实际可行性取决于 Phase 2 限额 |
| 数据与日志 | JSONL 任务/轨迹、CSV 指标；产物不提交 Git | 模型权重、缓存和大数据集通过配置指向服务器目录 |
| 版本管理 | Git + `.gitignore` + 配置模板 | 每次更新推送代码、文档和小型元数据；不推送密钥/权重/大文件 |

技术栈是启动假设。第一天核实本地环境和 Phase 2 登录/调度方式后，如果兼容性不佳，应尽早调整，而不是为栈本身耗费数日。

## 5. 任务、数据与评分设计

### 任务格式

每个任务包括：唯一 ID、仓库快照/版本、问题描述、允许工具、测试命令、隐藏测试、参考修复（可选）和元数据。任务输入不包含隐藏测试内容。

### 数据策略

- 优先从许可清晰的开源 Python 仓库和 bug 修复案例中挑选小任务。
- 首版以人工检查和本地可复现测试为准，先收集约 30–80 个任务即可；不追求大规模数据。
- 按仓库或问题来源拆分训练、验证、测试，减少相似补丁泄漏。
- 若公开任务的环境安装过重，改为我们维护的微型 Python 项目和合成/改写 bug，确保测试可稳定运行。
- 在 README 中记录来源、许可证、筛选规则和任何改写。

### 自动奖励（建议初版）

总奖励由可验证子项组成，具体权重在基线分析后冻结：

- 隐藏测试通过：主要任务奖励。
- 补丁可应用、代码可导入/语法有效：辅助奖励。
- 使用允许的工具并遵守格式：小额格式奖励或硬性校验。
- 超时、越权命令、未修改或破坏项目：惩罚或零任务奖励。
- 工具调用次数/运行成本：作为报告指标；首版不宜过度惩罚必要探索。

奖励规则必须在查看测试集结果前固定。训练奖励与最终测试指标分开报告，避免只报告模型在训练奖励上的提升。

## 6. 成功标准

### 必须交付（项目完成定义）

- 前端可选择任务并查看执行过程、结果和代码 diff。
- 后端能在预置任务上运行有限工具 Agent，并生成结构化轨迹。
- 任务运行有超时、错误处理和基本命令白名单。
- 有固定的数据划分和自动评测脚本，可重复计算任务成功率。
- 有基线结果、至少一轮后训练尝试及训练前后对比；若 GPU 配额或兼容性阻断训练，应提供可运行的训练配置、明确的阻断记录和已验证的 rollout/reward 流程。
- README 包含安装、运行、评测、训练、复现实验和演示步骤。
- Git 远程仓库有按里程碑推送的代码和文档。

### 期望指标（目标，不作为虚假保证）

- 初始任务集：30–80 条；测试集至少 10 条，优先保证质量而非数量。
- 基线与训练后模型在同一冻结测试集上比较 Pass@1、测试通过率、平均工具步数、超时率和推理成本。
- 至少完成 3 个固定演示任务，结果可复现。
- 训练报告如实给出样本数、GPU 型号、训练步数、超参数、失败案例和限制。

## 8. 每日工作节奏（3–4 小时）

- 15 分钟：回顾昨日交付和待办，确认当日一个可验收目标。
- 2–2.5 小时：集中实现当前核心功能。
- 30–45 分钟：运行最小验证、记录结果和问题。
- 15–30 分钟：更新 README/实验日志、提交 Git 并推送。
- 遇到远程 GPU 排队或环境问题时，先继续本地可推进工作：数据 schema、评分器、前后端、mock 模型接口和文档。

## 9. Git 与 GPU Farm 工作约定

- 建立一个 Git 远程仓库；本地开发后推送，服务器通过 `git clone` 或 `git pull` 获取代码。
- 至少在每天结束和每个功能可运行时提交；推送失败时记录原因并保留本地提交。
- 使用 `.gitignore` 排除 `.env`、API key、模型权重、缓存、虚拟环境、数据集大文件和运行日志。
- 提供 `.env.example` 和训练配置模板，不提交真实凭据。
- GPU Farm 使用前先在 gateway 登录，再按 Phase 2 文档申请计算节点；只在已分配 GPU 的计算节点上运行 `nvidia-smi` 和 CUDA 工作负载。
- Phase 2 官方 Quick Start 的示例为交互式 `gpu-interactive`，截图示例为 RTX 4080、16GB；实际 GPU 型号、可用显存、CPU/内存和限额以我们实际分配结果为准。
- 官方文档提示退出交互式计算节点会终止该节点上的进程；不把长训练依赖于断开的交互会话。确认 Phase 2 支持的批任务/会话时限后再安排长跑。
- 任何数据下载、许可证和服务器存储配额均须记录；模型与数据大文件不放入代码仓库。

## 10. 风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| Phase 2 任务队列/GPU 时长有限 | 训练迭代变少 | 第 1 天核实配额；先做短 smoke run；本地完成 agent 和评测 |
| 16GB 显存不适合大模型 RL | OOM 或 rollout 太慢 | 选小模型、LoRA/QLoRA、短上下文、小 batch；以实验记录为准调整 |
| 开源修复任务依赖难复现 | 评分器不稳定 | 自建微型仓库任务；锁定依赖；任务工作区隔离 |
| GRPO 奖励稀疏/方差大 | 训练无提升 | 先做基线和 reward 分布检查；小规模筛任务；保存完整轨迹 |
| 前后端占用过多时间 | 训练被挤压 | 使用最小可用界面；不做账号系统、复杂协作和部署平台 |
| GitHub 远程仓库尚未确认 | 无法立即推送 | 首日确定已有仓库或创建远程；推送前检查密钥和大文件 |

## 11. 项目差异化与简历呈现

差异化不是造一个新 RL 算法，而是把**可观察的 Agent 运行时、可验证的代码执行奖励和可复现的训练评测**放进同一个小型项目：每个模型决策都能追溯到工具调用和测试结果；训练/测试划分清晰；界面可以直观看到补丁及其质量。

完成后简历描述应根据真实结果填写，例如：

> 构建 RepoFix-RL 代码修复 Agent，使用 FastAPI/React 实现交互式轨迹与补丁展示；在隔离 Python 任务环境中接入基于隐藏测试的奖励，使用 [实际算法/模型/硬件] 完成参数高效后训练，并在固定测试集上将 Pass@1 从 [基线] 提升/变化至 [结果]，同时记录工具步数与运行成本。

若没有获得正向提升，就如实报告实验设置、失败原因和分析，不编造提升。

## 12. 首日开始前需要收集的信息

1. Phase 2 GPU Farm 账号是否已经开通；是否能够连接 HKU VPN/校园网并 SSH 到 gateway。
2. 本地是否已有 GitHub/GitLab 仓库，或是否希望首日建立新的远程仓库。
3. 实际获得的 GPU 资源、配额和软件环境，以登录计算节点后查询为准。

在仓库远程地址和账号就绪之前，可以先完成本项目书、目录设计和本地代码；推送步骤待远程配置后执行。
